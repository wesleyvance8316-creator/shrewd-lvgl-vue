## 1. 一个 GUI 程序到底在跑什么(从浏览器说起)

浏览器是目前最复杂的 GUI 程序,它的结构性选择经过了二十年打磨。先看清它,
嵌入式这边的取舍才有参照物。

### 1.1 线程模型

以 Chromium 为参照,一个页面大致有这么几类线程:

| 线程 | 干什么 | 能不能碰 UI 树 |
|---|---|---|
| **主线程(UI 线程)** | 解析 HTML、执行 JS、样式计算、布局(layout)、绘制(paint)、派发输入事件 | **能,且只有它能** |
| **合成线程** | 图层合成、独立滚动 | 不能,只搬图层 |
| **光栅/光栅化工作线程** | 把绘制指令转成像素 | 不能 |
| **网络/IO 线程** | socket、TLS、缓存 | 不能 |
| **Worker / Service Worker** | 纯计算 | **不能**(碰 DOM 直接抛异常) |

**关键不是线程多,而是"谁能碰 UI 树"这条边界画得很硬。**

线程之间的关系与那条硬边界(箭头是数据/任务的流向):

```
                  ┌──────────────────────┐
                  │     网络 / IO 线程   │
                  │   socket · TLS · 缓存│
                  └───────────┬──────────┘
                              │ 响应数据 → 排进主线程的任务队列
                              ▼
 ┌────────────────────────────────────────────────────────────┐
 │                     主线程(UI 线程)                        │
 │                                                            │
 │     解析 HTML ─► 执行 JS ─► 样式计算 ─► 布局 ─► 绘制       │
 │                                                            │
 │     ※ DOM 只能在这里被碰。别的线程碰 DOM 直接抛异常。      │
 └─────┬──────────────────────────────────────────────┬───────┘
       │ 已绘制的图层树                                 │ 可转移的纯计算任务
       ▼                                              ▼
 ┌─────────────────────┐                    ┌─────────────────────┐
 │       合成线程      │                    │  Worker / Service   │
 │   图层合成 · 滚动   │                    │       纯计算        │
 └─────────┬───────────┘                    │   禁止碰 DOM        │
           │ 光栅化任务                     └─────────────────────┘
           ▼
 ┌───────────────────┐
 │   光栅化工作线程   │──► GPU ──► 屏幕
 └───────────────────┘
```

注意三条**单向**的边:网络线程的数据只能排队进来;主线程的图层树只能交给合成线程;
Worker 只能接走"纯计算"。**没有任何一条边能让别的线程摸到 DOM。**

### 1.2 事件循环:渲染从不打断脚本

主线程的执行是一个循环:

    取一个任务(task)→ 跑到完成 → 清空微任务队列
      → (如果到该出一帧了)跑 requestAnimationFrame 回调
      → 样式计算 → 布局 → 绘制 → 交给合成线程

一轮跑起来是这样(时间向下):

```
 ┌──────────────────────────────────────────────────────────────────┐
 │  任务队列里躺着:输入事件 · 定时器 · postMessage · 网络回调       │
 │  (全是别的线程排队送进来的)                                      │
 └────────────────────────────┬─────────────────────────────────────┘
                              ▼
 ┌──────────────────────────────────────────────────────────────────┐
 │  ① 取一个任务,跑到完成                                           │
 │     · 派发事件、执行 JS 处理器                                   │
 │     · 期间改了 50 次 DOM:只是标脏,一个像素也没画                 │
 │     · 两个任务绝不交错(事实 A)                                   │
 └────────────────────────────┬─────────────────────────────────────┘
                              ▼
 ┌──────────────────────────────────────────────────────────────────┐
 │  ② 清空微任务队列(Promise 的回调在这里跑)                        │
 └────────────────────────────┬─────────────────────────────────────┘
                              ▼
 ┌──────────────────────────────────────────────────────────────────┐
 │  ③ 渲染 —— 只在任务之间,不在任务中间(事实 B)                     │
 │     · 跑 requestAnimationFrame 回调                              │
 │     · 样式计算 → 布局 → 绘制                                     │
 │     · 那 50 次改动在这里合成一帧                                 │
 └────────────────────────────┬─────────────────────────────────────┘
                              │ 图层树
                              ▼
 ┌──────────────────────────────────────────────────────────────────┐
 │  合成线程:图层合成 · 滚动 → 光栅化 → GPU → 屏幕                  │
 └────────────────────────────┬─────────────────────────────────────┘
                              ▲
                              │ 别的线程的数据在这里排队进入,
                              │ 成为下一轮的"任务"——回到顶部
```

**看图能直接得出两件事**:DOM 的 50 次改动没有产生 50 次绘制,批处理是循环结构给的;
而"渲染"是一个完整的阶段,不是穿插在 JS 里的动作。

有两条结构性事实值得记住,后面会反复用到:

**事实 A:JS 是单线程的,两个 JS 任务绝不交错。**
所以写 JS 不需要考虑"两个回调同时改同一个 DOM"。

**事实 B:渲染发生在任务之间,不在任务中间。**
所以一个任务里改 50 次 DOM,**只画一次**。批处理是内建的,不需要框架来做。

### 1.3 为什么浏览器要这么设计

因为 UI 树的并发修改需要锁,锁会带来死锁、优先级反转和不可复现的 bug。浏览器选择
"单线程 + 事件循环",用**换掉锁**来换确定性,代价是**任何一个长任务都会卡住 UI**。

这条取舍在嵌入式同样成立,而且更明显——嵌入式连"把长任务丢进 Worker"的退路都少。

## 2. Vue3 在解决什么问题

### 2.1 过程式 GUI 的真实痛点

先看一段嵌入式开发者天天在写的代码。设备卡片显示 `name`、`state`、`battery` 三个字段,
它们分别来自网络推送、传感器线程、定时器:

```c
/* 网络推送回调 */
static void on_name(void *c, const char *name) {
    card->name = name;
    lv_label_set_text(card->name_label, name);      /* 同步点 1 */
}

/* 传感器回调 */
static void on_state(void *c, int s) {
    card->state = s;
    lv_label_set_text(card->state_label, state_str(s));  /* 同步点 2 */
    if (s == STATE_FAULT) {
        lv_obj_add_flag(card->banner, LV_OBJ_FLAG_HIDDEN);  /* 同步点 3 */
    } else {
        lv_obj_remove_flag(card->banner, LV_OBJ_FLAG_HIDDEN);
    }
}

/* 定时器 */
static void on_battery(void *c, int b) {
    card->battery = b;
    lv_bar_set_value(card->bar, b, LV_ANIM_OFF);     /* 同步点 4 */
}
```

问题不在难,在**散**:

- **同步逻辑和状态逻辑纠缠**:上面四个回调同时在改数据和改 UI。
- **同一个状态的展示方散落多处**。现在要求"把 `name` 也显示在窗口标题栏"——
  你得找到每一个写了 `name` 的地方。**漏一处就是 bug,而且编译器不会告诉你。**
- **状态和视图没有边界**:哪份数据是真相?看代码看不出来,得靠约定。

需求再变一次(比如"FAULT 时标题也要变红"),散点又多一个。这就是过程式 GUI 在
业务复杂化后的真实代价。

### 2.2 Vue3 的三层

Vue3 不是一个整体,它分三层。**分层的收益是:一个反应核心,多个渲染器。**

```
  ┌───────────────────┐  ┌───────────────────┐  ┌───────────────────┐
  │   runtime-dom     │  │  runtime-native   │  │    小程序渲染器   │
  │   (浏览器 DOM)    │  │   (原生控件)      │  │                   │
  └─────────┬─────────┘  └─────────┬─────────┘  └─────────┬─────────┘
           │ 只需实现一个窄接口:nodeOps + patchProp
           │ (怎么创建 / 插入 / 改一个宿主节点)
           └──────────────────┬────────────────────────┘
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │   运行时核心 runtime-core                                │
  │   组件 · vnode · diff/patch · 调度器 · 生命周期          │
  └──────────────────────────┬───────────────────────────────┘
                             │ 只用下面这一层的能力
                             ▼
  ┌──────────────────────────────────────────────────────────┐
  │   反应核心 @vue/reactivity                               │
  │   ref · effect · computed · watch                        │
  └──────────────────────────────────────────────────────────┘
                             ▲
                             └── 这一层完全不知道 UI 的存在,
                                 可以单独拿去做别的事
```

**最底下那层是重点**:反应核心是一个**纯依赖图**,它不知道 DOM、不知道组件、
不知道渲染。它单独发布成 npm 包,可以被拿去做任何"一个值变了,别的东西跟着变"的场景。

这正是我们要学的地方:**反应核心不该长在 UI 库里,它应该是一个独立的、UI 无关的层。**
(本项目已经这么定了:反应核心在 shrewd-basic 的 reflect 模块,零 LVGL 依赖。)

### 2.3 反应核心的机制:三条规则

反应核心只有三条规则,没有别的:

**规则一,读即登记。** 在某个计算的执行过程中读一个值单元,就自动记下一条
"这个计算依赖这个单元"的边。

**规则二,写即通知。** 写一个值单元,自动重跑所有依赖它的计算。

**规则三,每轮重收。** 每次重跑之前,先把旧的依赖边全部清空,再重新登记。
所以分支里才读到的值,依赖关系跟着分支走。

画出来是这样。**先看依赖是怎么长出来的**——effect 运行时读到谁,就记下谁:

```
    值单元(ref)                            计算(effect)
    ┌──────────┐                           ┌──────────────────────────┐
    │   name   │ ───────── 读 ────────────►│  effect: 渲染卡片标题    │
    └──────────┘                           │    lv_label_set_text(...)│
    ┌──────────┐ ───────── 读 ────────────►│    读 name、读 state     │
    │  state   │                           └──────────────────────────┘
    └──────────┘
    ┌──────────┐                           ┌──────────────────────────┐
    │ battery  │ ───────── 读 ────────────►│  effect: 画电量条        │
    └──────────┘                           └──────────────────────────┘

    ↑ 这三条箭头没有一处是人声明的。effect 运行时读到谁,就记下谁。
```

**再看写的时候发生什么**——沿箭头找,自动重跑:

```
            ref_set(&name, "新名字")
                     │
                     │  沿订阅边找:谁读过 name
                     ▼
            ┌──────────────────────────┐
            │  effect: 渲染卡片标题    │   ← 重跑一次
            │   这次又读了 name、state │
            │   → 边被重新登记一遍     │   ← 规则三:先清空旧边,再重收
            └──────────────────────────┘

    画电量条那个 effect 没读过 name,所以它一动不动。
```

**注意第一张图里没有任何一行代码说"标题依赖 name"。** 那句话不存在,存在的只是
"标题这个 effect 读了 name"。依赖是被**发现**的,不是被**声明**的——这是 §3.2 里
讲的**登记手段**(手段①),不是响应式的定义。

三个概念由它们派生:

| 概念 | 是什么 |
|---|---|
| **ref(值单元)** | 一个存值的地方 + 一张订阅者名单 |
| **effect(计算)** | 一段会被自动重跑的代码,跑的时候自动收集依赖 |
| **computed** | 既是"计算"又是"值单元"的东西:派生值,自己也是别人的依赖 |
| **watch** | 带副作用的计算,拿到旧值和新值 |

## 3. 响应式的核心根本

### 3.1 根本:关系被声明,传播自动发生

先给定义:

> **你只声明"关系",系统负责让关系一直成立。**

数据变了,系统自动维持你声明过的那些关系,于是所有依赖处跟着变。
"一处数据变化,依赖它的地方自动跟着变"是这句话的**结果**。

注意根本不是"响应数据"这个动作本身——**过程式 GUI 同样在响应数据**(§2.1 那三个
回调就是)。区别在别处:

| | 关系写在哪 | 谁负责传播 |
|---|---|---|
| **过程式** | **不写关系**,只在每个变化点写"更新动作" | 人:N 个变化点 × M 个显示处 |
| **响应式** | 关系集中声明:M 处 | 系统 |

过程式真正缺的不是"响应",而是**"关系"这个概念没有位置**。`label 显示 name` 这句
话在代码里没地方可写,你只能在"改 `name` 的地方"写"把 label 也改一下"。于是同步
散落在每个变化点上——这就是 §2.1 那四个同步点的来历,也是"漏写一处"的来历。

换成响应式,那四个同步点全部不存在:你只声明"这个 label 显示的是 `name`",改
`name` 的地方不关心谁在显示它,显示的地方不关心谁在改它。**"漏写一处"这个错误
类别在结构上消失了**,因为没有一处可以漏。

收益随复杂度增长:状态被用得越散、变化来源越多、需求越常变,过程式那边的手写同步
增长越快,而关系声明这边不增长。

### 3.2 难点在"谁依赖谁":两种手段

关系要成立,系统必须知道**谁依赖谁**。这一步有两种做法,**两者都是响应式**,
差别只在"关系由谁给":

| 手段 | 依赖怎么来 | 代表 |
|---|---|---|
| **① 自动发现**(读即登记) | 运行关系体时,读到谁就记下谁 | Vue / MobX / Solid |
| **② 显式声明**(依赖清单、订阅) | 另外写一份"我依赖谁" | 电子表格公式 / RxJS / React 的 `useEffect(fn, [deps])` |

反例能说明定位:**电子表格 `C1 = A1 + B1` 里,依赖是显式写在公式里的**,可它毫无疑
问是响应式的。所以"依赖是发现的"不是响应式的定义,是**登记手段的选择**。

**本项目选 ①**(§2.3 那三条规则讲的就是它)。理由不是"② 不算响应式",而是:

> **手段②让关系被写两遍**:函数体里一次(`A1 + B1`),依赖清单里一次(`[A1, B1]`)。
> 两份会走散——React 的 missing-dep、stale-closure 就是这么来的。
> **手段①只写一遍**:依赖是从函数体里读出来的,没有第二份,也就没有走散这回事。

所以 ① 的价值是**少一处会出错的重复**,不是"它才是响应式"。把"依赖是发现的,不是
声明的"当成根本,是把实现特性当成了定义。

### 3.3 它不是魔法

对响应式有抵触,通常抵触的是"看不见的自动行为"。但本项目这一套(手段①)的实际机制是:

- **一个图 + 三条规则**,没有别的。依赖图可以打印,谁依赖谁一目了然。
- **它不改变执行模型**:还是同步的、单线程的、顺序执行的。没有后台调度、没有隐式并发。
- **它不夺走控制权**:ref 可以显式读写,effect 可以手动重跑或销毁,绑定可以拆掉。
  它是**加一层自动化**,不是换一套编程模型。
- **失败模式只有三个,都可以点名**:

| 失败模式 | 是什么 | 怎么处理 |
|---|---|---|
| **回路** | 写 A → 触发效果 → 写 B → 触发效果 → 写 A | 显式抑制(见 design.md §4) |
| **生命周期** | 依赖图活得比它描述的状态久 → 悬挂引用 | 绑定随 widget 死(见 design.md §3) |
| **漏跟踪** | 依赖边没建上 → 改了不刷新(手段①固有:登记要分配边,分配会失败) | 记入排查手册 |

这三个都是**可命名、可检测、可设计**的,不是"出问题只能猜"。后面两份文档正是
在把这三条逐条钉死。

### 3.4 代价与前提(诚实一节)

响应式不是免费的,说清代价才配谈方案:

- **有学习成本**:要知道哪些读会被跟踪、什么时候会重跑。边界必须写清楚。
- **调试时栈更间接**:异常可能在"自动重跑"的栈里抛出,而不是你调用的那个函数。
  好在我们的 effect 是同步的,调用栈仍然可读,这点比浏览器友好。
- **同步传播不等于批处理**:N 次写可能跑 N 次效果。对 UI 绑定无感(见 §4.2),
  对昂贵的派生计算有感。
- **不适用的场景也得说**:一个屏、三个字段、需求不再变——**过程式完全够,别上响应式**。
  它的价值来自复杂度,不来自时髦。

## 4. 映射到嵌入式:LVGL 已经是 retained

### 4.1 retained 与 immediate

GUI 有两种根本不同的存在方式:

- **立即模式(immediate mode)**:像 Dear ImGui。每帧重新描述一遍界面,
  "界面是这一帧的函数"。没有对象,没有状态,每帧重建。
- **保留模式(retained mode)**:像 Qt、GTK、DOM、**LVGL**。你创建对象,
  对象持续存在,你改它的属性,框架负责重绘。

**LVGL 是保留模式**:你 `lv_label_create()` 出来的 label 是一块活着的内存,
里面有文字、位置、样式;`lv_label_set_text()` 是**改一个结构体字段 + 标脏**,
不是"重新描述这个 label"。

这一点决定了后面所有的取舍。

### 4.2 于是不要 vdom

Vue 需要虚拟 DOM(vdom),原因是三个:

1. 它的 API 是**声明式**的——"UI 是状态的函数"。要把这句话变成一串 DOM 操作,
   必须知道**变了什么**,于是要对比前后两份描述。
2. DOM mutation 相对贵:改属性会触发样式重算、布局,可能级联。
   所以要把操作数量压到最小。
3. DOM API 本身是字符串/节点式的、难写,vnode 是个好用的中间表示。

**LVGL 这三条全不成立:**

1. 没有"声明式描述"要对比——你直接改对象。
2. `lv_*_set_*` 是结构体写 + 标脏,**便宜**。
3. 调用 LVGL API 本来就直接。

而且 LVGL 的重绘是**合并的**:多次 `lv_*_set_*` 只是反复标脏,真正绘制发生在
`lv_timer_handler()` 的那一帧。所以"批量"这件事 LVGL 已经做了。

**结论:vdom 的工作在 LVGL 这边根本不存在。** 这不是"省略一个优化",而是
**它要解决的问题在这里不成立**。立项文档把它列为非目标,理由就在这里。

但有一样东西要保留:**key 对账**。Vue 靠 vdom 做 keyed list 的最小增删移动;
我们没有 vdom,所以自己做一个**按 key 的最小对账**(缺则建、多则删、乱则移),
不做 diff 算法。

### 4.3 线程模型对照

| | 浏览器 | LVGL |
|---|---|---|
| UI 树 | DOM | `lv_obj_t` 树 |
| 谁能碰 UI 树 | 只有主线程 | 只有 UI 线程 |
| 事件循环 | 内建、藏起来 | `lv_timer_handler()`,**显式** |
| 一次循环干什么 | 取任务 → 跑完 → 微任务 → 渲染 | 跑定时器 → 分发事件 → 刷新脏区 |
| 改 UI 的代价 | 贵(会触发布局) | 便宜(标脏) |
| 批处理 | 同任务内 mutation → 一次 paint | 同帧内多次 set → 一次绘制 |
| 非 UI 侧并发 | Worker / 网络线程 | 业务线程 / 总线分发线程 |

**同构处**:都是单 UI 线程 + 事件循环;都在非 UI 线程产生数据,都必须送回 UI 线程。

**关键差异**:浏览器把事件循环**藏起来**了——前端开发者从不需要写主循环。
嵌入式**不能藏**,因为主循环本来就是调用方的:

```c
while (1) {
    /* 你的业务 */
    lv_timer_handler();
    usleep(5000);
}
```

这一条直接推出 lvgl-vue 的线程契约:**不隐藏线程**。

**本节只是对照,不是本项目的线程模型。** lvgl-vue 有哪几个线程、各自跑什么、
数据和事件怎么跨线程流转,见 **§7.3「线程模型」**——那里有职责表和三张流转图。
先在这里给一句结论:

> 有 **UI 线程**(唯一能碰 `lv_obj_t`)、**sb_dbus 分发线程**、**业务/采集线程**;
> **数据下行要跨线程投递,事件上行全程在 UI 线程内**。

## 5. 模型:数据、事件、页面

这是本文的落点。前面都是为了把这三者的关系说清楚。

### 5.1 简化模型:两个主体

先给能记住的那一层,后面全是它的展开:

```
                            外部世界:网络 / 其他进程 / 传感器
                                     │
                                     │   ① 进 / ④ 出
                                     ▼
        ┌──────────────────┐                       ┌──────────────────┐
        │       状态        │ ──── ② 自动传播 ────► │       页面        │
        │  (数据,唯一中枢)  │                       │ (UI,LVGL 对象树) │
        └──────────────────┘ ◄─── ③ 事件写回 ────  └──────────────────┘
```

**就两格。** 页面不直接读外部,外部也不直接改页面——都经过状态。

展开成四条流,**「谁负责」这一列就是本库的分工**:

| 流 | 从 | 到 | 谁负责 | 性质 |
|---|---|---|---|---|
| ① | 外部世界 | 状态 | 桥(经 sb_dbus 进来) | 异步、跨线程,需投递 |
| ② | 状态 | 页面 | **绑定层(响应式)** | 同步、自动、零接线 |
| ③ | 页面 | 状态 | 事件写回 | 同步、在 UI 线程内 |
| ④ | 状态 | 外部世界 | 桥(提交) | 可选 |

**`v-model` 不是第三种东西,就是 ② + ③。** 双向绑定的本质是两条单向。

**这一对主体的物理面在 §7.3**:状态那侧的执行者叫**数据"线程"**,页面那侧的执行者
叫 **UI 线程**,中间隔着一条线程边界。本节讲**逻辑面**——谁是真相、谁是投影;
§7.3 讲**物理面**——哪几个线程在跑。同一对主体,两种看法。

### 5.2 为什么必须汇到一处

四条流方向各不相同,但**都汇到"状态"这一格**。原因有三:

1. **同一个状态常有多个显示处**。`name` 既在卡片里,也在标题栏。只有汇到一处,
   才不会有"这里更新了那里忘了"。
2. **变化来自任意方向**。网络推送、用户点按、定时器、其他进程——不汇到一处就没有一致性。
3. **跨线程/跨进程**。外部数据不能直接碰 widget(§4.3),它必须先变成状态,
   再由状态在 UI 线程推到页面。

拓扑上看得最清楚。下面两幅是同一批来源、同一批显示处,**唯一区别是有没有中枢**:

```
  ① 没有中枢 —— 每加一个显示处,要改 N 处

     来源                显示处
     网络推送 ──┬──► 标题栏
                ├──► 卡片
                └──► 状态栏
     定时器    ──┬──► 标题栏
                ├──► 卡片
                └──► 状态栏
     用户点按  ──┬──► 标题栏
                ├──► 卡片
                └──► 状态栏

     3 个来源 × 3 个显示处 = 9 处手写同步
     要加第 4 个显示处?── 改 3 处(每个来源各一处)
```

```
  ② 有中枢 —— 每加一个显示处,只加 1 处

     网络推送 ──┐
     定时器    ──┤
     用户点按  ──┼──►  ┌──────┐  ──┬──► 标题栏
     其他进程  ──┘     │ 状态 │     ├──► 卡片
                       └──────┘     ├──► 状态栏
                                    └──► 列表项

     来源各写 1 处 + 显示处各绑 1 处 = 3 + 3 处
     要加第 4 个显示处?── 只加 1 条绑定声明
```

差别不在连线数量,在**改动的成本落在谁身上**。没有中枢时,每加一个显示处要动
每一个来源;有中枢时,来源不知道谁在看它,显示处不知道谁在改它。

### 5.3 MVVM 合流

立项文档定的 MVVM,在这里有了明确的落位:

| MVVM | 是什么 | 本项目的落位 |
|---|---|---|
| **Model** | 数据的真相,通常是外部的 | **sb_dbus**(类型化命名空间 + 钩子 + 通知管道) |
| **ViewModel** | Model 的投影,页面可以直接绑定的东西 | **反应核心(shrewd-basic reflect)+ 绑定层(本仓)** |
| **View** | 用户看到的 | **LVGL**(retained 对象树) |

把 §5.1 那四条流套到这三段上,落位就具体了:

```
                            ④ 提交
                       ┌────────────────────────────┐
                       │  Model ── sb_dbus          │
                       │  数据的真相                │◄────────── 外部世界
                       └───────────┬────────────────┘     ① 数据进入
                                   │                     (跨线程,需投递)
                                   │  投影(Model 的一个视图)
                                   ▼
                       ┌────────────────────────────┐
                       │  ViewModel ── 反应核心     │
                       │  + 绑定层(本仓)            │
                       └───────────┬────────────────┘
                                   │  ② 自动传播(响应式)
                                   ▼
                       ┌────────────────────────────┐
                       │  View ── LVGL 对象树       │
                       │  用户看到的                │
                       └───────────┬────────────────┘
                                   │  ③ 事件写回(用户操作)
                                   └─────────► (回到 ViewModel)
```

注意 **ViewModel 是双向的两端**:② 从它下去,③ 回到它;而 Model 和 View 之间
**没有任何直接连线**。这就是"把手写同步删掉"的形态——同步不是被优化了,
是被挪进了绑定机制里。

顺带说清 MVVM 和 MVC 的差别,因为嵌入式朋友多半更熟 MVC:

- **MVC**:Controller 接输入,并且**负责把 Model 同步到 View**。问题是这个同步是
  **手写的代码**——Controller 很容易长成上帝对象,而且 §2.1 的散点问题原样存在,
  只是从回调搬到了 Controller。
- **MVVM**:把"Model → View 的同步"这件事从**代码**变成**声明**。ViewModel 是
  Model 的一个投影,View 只跟 ViewModel 打交道,同步交给绑定机制。

所以 MVVM 不是又一个分层游戏,它是**把手写同步这件事从程序里删掉**。

### 5.4 过程式在这里会崩

**过程式 GUI 把这三条流混在一起**:§2.1 那段代码里,网络回调既改数据又改 UI,
事件回调既改数据又改 UI。一旦"状态"这个概念没有独立的位置,散就是必然的。
拿那个设备卡片对照一遍:

| | 过程式 | lvgl-vue |
|---|---|---|
| 三个字段各显示一次 | 3 个同步点 | 3 条绑定声明 |
| `name` 也要进标题栏 | 再找地方加同步点 | 再绑一次 |
| FAULT 时标题变红 | 又一个散点 | 又一条声明 |
| 漏写一处 | **编译通过,运行出错** | **结构上不存在** |
| 谁是数据真相 | 靠约定 | 状态就是 |

但也要说清**它救不了什么**:如果数据本身来自三个线程,你仍然要把它们送到 UI 线程
(§7.3);如果状态结构设计得差,响应式只是把差的设计自动化了。**它消灭的是
"手写同步"这一类 bug,不是设计问题。**

## 6. 页面管理

> **本节是机制面,不是业务面。** 框架的价值恰恰是让使用者不必回答"页面多不多、
> 关系复不复杂"——那些问题该由框架吃掉,不该留给使用者。
>
> 标杆是 **vue web 开发者的不操心**:他们不写组件何时创建/销毁、不管内存、不用
> 手动接线。GUI 世界这些全要自己管。**这一层就是本框架要补的那部分。**
> 前提:面向嵌入式 Linux,**资源必然受限**;且本框架是通用框架,不是某个项目的定制。

### 6.1 验收标准:使用者不该碰的事

| 不该碰 | 手写 LVGL 时会怎样 |
|---|---|
| 何时创建页面 | 手动 `lv_obj_create` |
| 何时销毁页面 | 手动 `lv_obj_delete`,漏了就是泄漏 |
| 何时进入 / 离开 | 手动接订阅、起停定时器、加载 / 保存 |
| 内存够不够 | 自己算、自己取舍 |
| 返回去哪 | 自己维护栈,或写死 |
| 跳转的接线 | 每个按钮写一个回调 |

**机制成立与否,就看上面每一行是否都变成了"声明",而不是"动作"。**

### 6.2 生命周期:四阶段(已决)

不是"进入/离开"两阶段,是**四阶段**:

```
     创建 ──────► 激活 ──────► 失活 ──┬──────► 激活 ──► 失活 ──► …   缓存:回到激活
                                       │
   建 widget + 挂绑定      enter  exit └──────► 销毁                        释放
                            │      │              │
                          订阅   退订            dispose
                          加载   保存
```

**为什么必须分开**:

- **创建 ≠ 激活**:缓存的页面已经建好了,但每次进入仍要 `enter`(刷新数据、重新订阅)。
- **失活 ≠ 销毁**:缓存的页面失活但不销毁,下次进入不用重建。

于是两件事被分到两对上,不再混着:

| 要决定的事 | 落在哪一对 |
|---|---|
| **页面什么时候释放** | 创建 / 销毁 |
| **进入 / 离开做什么** | 激活 / 失活 |

**框架保证**:四个钩子**顺序确定、一定被调用、不重入**。使用者只填钩子体,
不写调用时机。

### 6.3 状态与视图分离 → 敢释放(已决)

嵌入式不敢释放页面,是怕**丢状态**(填了一半的文本、滚到哪、选了什么)。手写 LVGL
里状态常长在 widget 上,删 widget 就丢,所以只能常驻,于是吃内存。

但 lvgl-vue 的**状态和视图本来就是分开的**(§3 的根本)。状态是 ref,活在组件的
状态 struct 里;widget 只是它的投影。

> **销毁页面只销毁视图,状态不丢。**

于是"离开即销毁"这个最省内存的策略**代价变得很低**——重建时状态还在,绑定一挂
就恢复。这是 web 都没做到的(web 组件状态长在组件里,卸载即丢),而且它恰好把
"资源受限"和"不丢状态"这对矛盾解开了。

**结论:内存策略可以默认激进,不必默认保守。** 这直接对应"不用担心资源"这个目标。

### 6.4 机制的完整面

| 层 | 是什么 | 框架保证 | 使用者写 |
|---|---|---|---|
| **导航状态** | 一个可绑定的状态 | 可被任何事件 / 模块改,有变更通知 | 无 |
| **页面注册表** | 声明有哪些页面 | 查找、按名或按值定位 | 每页一条声明 |
| **页面描述** | 创建 / 激活 / 失活 / 销毁 四钩子 + 释放策略 | 四钩子顺序确定、一定被调用 | 钩子里写业务 |
| **页面宿主** | 承载页面的容器 | 按导航状态建 / 换 / 释放 | 无 |
| **触发** | 事件(点按 / 超时 / 告警 / 状态) | **复用已有事件模型,零新机制** | 只管改导航状态 |
| **守卫** | 离开前允许否 | 拦截、可否决 | 判断逻辑 |
| **释放策略** | 何时销毁 | 按策略自动决定,**使用者不调 delete** | 选策略 |

### 6.5 释放策略:按页声明(已决)

不引入预算制(总内存上限 + 自动淘汰),**按页声明策略就够**:

| 策略 | 语义 | 代价 |
|---|---|---|
| **常驻** | 建一次不销毁 | 最快,最吃内存 |
| **离即销毁** | 失活即销毁 | 最省内存,每次重建 |
| **缓存 N 个** | 栈上留 N 个,超出淘汰 | 折中 |

**默认「离即销毁」**——靠 §6.3 把重建代价压低;需要的页面再覆盖成常驻或缓存。

### 6.6 触发就是事件;守卫是唯一特有概念

**触发没有新机制**:点按、超时、告警、状态变化——它们本质都是事件,只是触发者
不同。导航的触发**复用已有事件模型**,框架不需要"导航引擎的触发器"。

```
     触发(事件)  ──►  导航状态(状态)  ──►  页面(状态的函数)
     点按 / 超时 / 告警 / 状态变化
```

但**守卫不是事件**:事件回答"发生了什么",守卫回答"允不允许"。导航有一个别的
动作没有的东西——**它会离开当前页**。所以"能不能走"这个拦截只对导航有意义,
**守卫是唯一剩下的导航特有概念**。

## 7. lvgl-vue 的架构

### 7.1 分层

```
  ┌──────────────────────────────────────────────────┐
  │  组件层(使用者写)                                │
  │  状态 struct + 创建函数 + 销毁函数                  │
  ├──────────────────────────────────────────────────┤
  │  绑定层(本仓 shrewd-lv-view)                      │
  │  text / range / v-model / 列表对账 / 组件生命周期   │  ← 唯一引用 LVGL API 的地方
  ├──────────────────────────────────────────────────┤
  │  反应核心(shrewd-basic reflect)                   │
  │  ref / effect / computed / watch                   │  ← 零 LVGL 依赖
  ├──────────────────────────────────────────────────┤
  │  View:LVGL(retained 对象树)                     │
  └──────────────────────────────────────────────────┘

  横向:桥(sb_dbus ⇄ 状态)—— 也只在本仓,同样只在 UI 线程碰 LVGL
```

**边界要点**:

- **LVGL API 只在一个地方被引用**——本仓的绑定层与桥。Model(sb_dbus)与反应核心
  都是零 LVGL 依赖。这就是为什么反应核心可以放在 shrewd-basic 里而不用搬回来。
- **组件层是使用者的地盘**,本库不替他写组件,只提供绑定原语与生命周期约定。
- **从下往上看**:View 不知道反应核心的存在;反应核心不知道 LVGL 的存在;
  只有绑定层同时认识两边。**这层"翻译"就是本库的全部内容。**

### 7.2 照抄什么、不照抄什么

**照抄的**(因为 LVGL 与浏览器同构,§4.3):

| 照抄 | 理由 |
|---|---|
| 单 UI 线程 + 事件循环 | LVGL 同构 |
| 数据经状态汇流 | 一致性需要 |
| **关系声明 + 自动传播** | 这是响应式的心脏,与 UI 无关(§3.1) |
| **依赖自动发现** | 上一行的登记手段,取"关系只写一遍"这个好处(§3.2) |
| key 对账(列表) | 保留模式都需要,只是不走 vdom |

**不照抄的**(因为前提不成立):

| 不照抄 | 理由 |
|---|---|
| **vdom / diff / patch** | LVGL 对象树本就持久,`lv_*_set_*` 就是更新(§4.2) |
| **vnode / 组件的虚拟表示** | 没有 vdom 就没有 vnode。组件 = 状态 struct + 函数 |
| **模板编译 / 代码生成** | 使用者是纯 C 开发者,API 即产品 |
| **调度器 / nextTick / 微任务批处理** | LVGL 的重绘本就合并到一帧;我们的 effect 同步且已挡重入 |
| **Pinia / VueX / Router / SSR** | 与目标无关 |
| **隐藏线程** | 主循环是调用方的(§7.3) |

关于**调度器**要诚实一句:Vue 的调度器把多次写合并成一次效果重跑,我们是同步的、
N 次写可能跑 N 次效果。对 UI 绑定没差别(效果就是一次 `lv_*_set_*`,重绘照样合并);
对昂贵的派生计算有差别。**先不做**,等真实页面原型倒推时再判断值不值。

### 7.3 线程模型

一个跑起来的 lvgl-vue 程序里有哪几个线程、各在干什么、数据和事件怎么流转。
§4.3 只讲了浏览器和 LVGL 为什么同构,这里才是本项目自己的答案。

#### 简化模型:两个主体

先给能记住的那一层,后面全是它的展开:

```
        数据"线程"  ──────  投递  ──────►  UI 线程
        (0..2 条真实线程的统称)             (恒定 1 条)
```

**就这两格。**

- **UI 线程**:恒定 1 条。跑 `lv_timer_handler()`,是**唯一**能碰 `lv_obj_t` 的线程。
- **数据"线程"**:数据侧执行者的**统称**,不是某一条线程。真实线程数是 0..2。

> 这是**物理面**。同一对主体的**逻辑面**在 **§5.1**:那边叫「状态」与「页面」,
> 讲谁是真相、谁是投影;这里讲哪几个线程在跑。

| 真实线程数 | 什么时候 | 是哪几条 |
|---|---|---|
| **0** | 数据就在 UI 线程上产生 | 没有独立线程——数据侧**退化进 UI 线程** |
| **1** | 纯进程内(`create`) | sb_dbus 的分发线程 |
| **2** | 跨进程(`attach`) | 分发线程 + shm wake 线程 |

**为什么可以用一个名字概括**:从 UI 线程的视角看,数据侧内部是 1 条还是 2 条线程
**完全无差别**——它只看到"通知被送过来"。而且投递点是单线程的(所有通知最终由分发线程
投),顺序性也无差别。

**但有一条不能跟着抽象走:**

> **数据"线程" ≠ UI 线程。**

中间那条**线程边界**,就是桥存在的唯一理由。上表"0"那一行恰恰是**边界消失**的
情形——数据侧退化进 UI 线程,桥也不需要。

#### 数据侧内部:几条线程、各是什么

真实线程数取决于部署,但**都属于 sb_dbus,由它自己 `pthread_create`,不跑在任何人的
loop 里**。所以 sb_dbus 是"自带线程的库",不是寄生在某个 loop 上的回调集。

| 线程 | 谁起的 | 干什么 | 何时有 |
|---|---|---|---|
| **分发线程** | `shrewd_basic_dbus_create()` | 从 FIFO 队列批量取通知,逐个 `recv` 投给订阅者 | `sync_notify=0`(默认) |
| **wake 线程** | `shrewd_basic_dbus_attach()` | 扫 shm 变更环,把**别的进程**写的条目喂进本进程的队列 | 仅跨进程 |

**分发机制**(两条线程串起来的样子):

1. `set()/publish()` 走完钩子后**入 FIFO 队列**(同路径未投递的可折叠,只留最新快照);
2. 分发线程**一次取走整队**成一个 batch;
3. 逐条 `recv`,再对每个订阅者调一次 `recv_batch`——高频写者被合并成一次回调;
4. **保序**:FIFO + 单线程投递,顺序确定。

跨进程那一半:写进程 `set()` → 写入 shm 变更环;读进程的 wake 线程扫到(**跳过自己
进程的条目**——本地已经通知过了)→ 喂进本进程队列 → **本进程的分发线程**投递。
**回调永远在接收方进程里跑,不跨进程执行。**

> 反面(`sync_notify=1`):投递内联到**调用者线程**,若多个线程同时 `set` 就没有全局
> 顺序了。这是测试/关停用的开关,不作为正常形态。

#### sb_dbus 是什么(先说清,否则图会画错)

sb_dbus 不是链条上的一个环节,是**数据总线**:一个类型化命名空间 + 钩子 + 通知管道。
它**本身不是线程**,是数据面。两件事容易混:

- **钩子在调用者线程里同步跑**。业务线程调 `shrewd_basic_dbus_set()` 时,钩子就跑在
  那条业务线程上。
- **变更通知由它自己的分发线程异步扇出**(`sync_notify` 打开则改为内联派发)。
  所以"分发线程"是总线的一部分,不是数据流上游的一个节点。

于是拓扑是**扇入扇出的中枢**,不是串行链:

> **所有跨模块/跨进程的数据都流向 sb_dbus**——它是 Model,是唯一的真相入口。
> 业务线程、其他进程、UI 的提交统统写进来;谁要数据,就订阅它。

(纯界面呈现状态,比如某个面板展开没展开,是 ViewModel 的局部状态,不必过总线。)

#### 全体线程名单

把上面两格展开成完整名单(「落在」一列对应简化模型的两格):

| 线程 | 落在 | 谁起的 | 干什么 | 能碰 `lv_obj_t` |
|---|---|---|---|---|
| **UI 线程(主循环)** | UI 线程 | 调用方的 `main` | 跑 `lv_timer_handler()`;**所有** effect、绑定写回、绘制;用户确认后写回 sb_dbus | **能,只有它能** |
| **sb_dbus 分发线程** | 数据"线程" | sb_dbus | 投递通知;**桥的订阅回调跑在这条线程上**(拷快照 → 入队 → 投递) | 不能 |
| **sb_dbus wake 线程** | 数据"线程" | sb_dbus | 扫 shm 变更环,喂进本进程队列(仅跨进程) | 不能 |
| **业务 / 采集线程**(可多个) | 数据侧生产者 | 调用方 | 传感器、协议解析、设备 IO —— **产出数据,写进 sb_dbus** | 不能 |
| **其它工作线程**(可选) | — | 调用方 | 任何耗时计算 | 不能 |

#### 谁在跑

```
     ┌────────────────────┐   ┌────────────────────┐
     │  业务 / 采集线程   │   │  其他进程 / 模块   │
     │  传感器、协议、IO  │   │                    │
     └─────────┬──────────┘   └─────────┬──────────┘
               └────────────┬───────────┘
                            │   set() / touch()
                            │   (钩子在调用者线程同步跑)
                            ▼
     ╔═════════════════════════════════════════════════╗
     ║   sb_dbus ── Model / 数据总线                    ║
     ║   类型化命名空间 + 钩子 + 通知管道                ║
     ║   ※ 它是数据面,不是线程                          ║
     ║   ※ 谁改数据谁写进来;通知由它扇出                ║
     ╚═══════════════════════════╤═════════════════════╝
                                 │  通知扇出
                                 │  (sb_dbus 的分发线程异步派发)
                                 ▼
     ┌─────────────────────────────────────────────────┐
     │   sb_dbus 分发线程                                │
     │    桥的订阅回调跑在这里:拷一份快照 → 入队 → 投递   │
     │    ※ 禁止碰 widget                                │
     └───────────────────────┬─────────────────────────┘
                             │  入队 + 投递(唯一的跨线程动作)
                             ▼
     ┌─────────────────────────────────────────────────┐
     │   UI 线程 ── 调用方的主循环                        │
     │                                                 │
     │      while (1) {                                │
     │          /* 你的业务 */                          │
     │          lv_timer_handler();  ← 一轮事件循环     │
     │      }                                          │
     │                                                 │
     │    ※ 唯一能碰 lv_obj_t 的线程                     │
     │    ※ 所有 ref_set / effect / 绑定写回都在这里跑   │
     │    ※ 用户确认后也写回 sb_dbus(UI 同时是生产者)   │
     └─────────────────────────────────────────────────┘
```

#### 数据怎么流(下行:外部 → 页面)

```
     业务/采集线程、其他进程产生状态变化
                │
                │  set() / touch() → 写进 sb_dbus
                ▼
     ╔════════════════════════════════╗
     ║   sb_dbus(Model / 数据总线)    ║   ← 数据面,不是线程
     ╚═══════════════════╤════════════╝
                         │  ① 变更通知扇出
                         ▼
     ┌────────────────────────────────────────┐
     │   sb_dbus 分发线程                       │   ← 别的线程
     │    ② 桥的订阅回调:拷一份快照             │
     │       (不能拿指针跨线程)                 │
     │    ③ 入队                                │
     └───────────────────┬────────────────────┘
                         │  ④ 投递(lv_async_call,或 eventfd + lv_timer)
                         │     ※ 唯一的跨线程动作
     ════════════════════╪═══════════════════════ 线程边界 ═══
                         ▼
     ┌────────────────────────────────────────┐
     │   UI 线程(lv_timer_handler 的一轮)    │
     │    ⑤ 一次出队全部快照(批量)            │
     │    ⑥ 逐个 ref_set                       │
     │    ⑦ effect 同步重跑 → lv_*_set_*       │
     │    ⑧ 本帧绘制一次(LVGL 自己合并)       │
     └────────────────────────────────────────┘
```

#### 事件怎么流(上行:用户 → 状态)

```
    用户按下 / 拖动
               │
               ▼
    ┌────────────────────────────────────────┐
    │  UI 线程(lv_timer_handler 的一轮)      │  ← 全程不跨线程
    │   ① 读输入设备                         │
    │   ② 派发 LVGL 事件                     │
    │   ③ 绑定的写回回调                     │
    │   ④ ref_set → effect 重跑 → 更新别处   │
    │   ⑤ (可选)把状态提交回总线             │
    └────────────────────────────────────────┘
```

**注意这两条流的不对称,它是理解本模型的关键:**

> **数据下行要跨线程,事件上行不跨。**
> 外部数据产生在别的线程,必须投递进来;而用户操作是 `lv_timer_handler` 在 UI 线程
> 里读出来的,从头到尾没离开过这个线程。所以 `v-model` 的写回**不需要任何跨线程
> 处理**,它就是一次普通的函数调用。

批量是关键:50 个字段变化不该唤醒 UI 线程 50 次。一次投递吃掉整队,由反应图去重,
由 LVGL 合并重绘。

#### 契约

浏览器把事件循环藏起来了,所以前端开发者感觉不到线程。嵌入式不行——主循环是调用
方的代码(§4.3),藏起来反而让他不知道自己的程序在跑什么。

**只有一条:**

> **所有 `ref_set` 必须发生在跑 `lv_timer_handler()` 的那个线程。**

因为 `ref_set` 会**同步**重跑效果,效果里是 `lv_*` 调用。在别的线程写 ref
= 在别的线程碰 UI 树 = 未定义行为。于是桥的职责被限定得很清楚:**它只做投递,
不做任何魔法**。

**这条契约对使用者是可见的**,他看得见自己在做跨线程投递。这正是立项文档
"不隐藏线程"那个非目标的落地形态。

## 8. 术语表

给不熟前端的读者。design.md 会直接用这些词。

| 词 | 意思 |
|---|---|
| **保留模式 / retained** | UI 元素是持续存在的对象,你改它的属性。LVGL 是这种 |
| **立即模式 / immediate** | 每帧重新描述界面,不保留对象。Dear ImGui 是这种 |
| **虚拟 DOM / vdom** | UI 的一份可对比的中间描述,用来算出最小改动。**本项目不用**(§4.2) |
| **ref / 值单元** | 一个存值的地方 + 订阅者名单 |
| **effect / 计算** | 一段会被自动重跑的代码,跑时自动收集依赖 |
| **computed** | 派生的值单元:既是计算,又能被别人依赖 |
| **watch** | 带副作用的计算,拿到旧值和新值 |
| **依赖追踪 / track** | 读一个值时记下"谁读了它" |
| **触发 / trigger** | 写一个值时重跑所有读过它的计算 |
| **依赖自动发现 / auto-tracking** | 依赖靠"读的时候记下来"取得,不是另外写一份清单。**这是手段,不是定义**(§3.2) |
| **响应式 / reactive** | 关系被声明,系统自动维持关系成立——数据变化自动传播。**不是**"自动美化 UI"(§3.1) |
| **事件循环 / event loop** | 取任务 → 跑完 → 渲染 的那个循环 |
| **v-model** | 双向绑定 = 状态→页面 + 页面→状态 两条单向 |
| **MVVM** | Model / ViewModel / View 分层,把手写同步变成声明 |
| **key 对账** | 列表渲染时按稳定标识最小增删移动子项 |
